# Аудит проекта `hh-bot` + `hh-applicant-tool`

Дата: 2026-03-03

Ниже собран технический фидбек по всему проекту, включая подмодуль `hh-applicant-tool`: что конкретно плохо, почему это плохо, чем это грозит и что стоит улучшить в первую очередь.

## Критичные и важные проблемы

## Список улучшений и ожидаемое влияние

| Улучшение | Что изменить | Влияние на проект |
|---|---|---|
| Защитить секреты | Шифрование/secret-store, отказ от plaintext, безопасный backend по умолчанию | Снижение риска компрометации аккаунтов и утечек данных |
| Включить quality gate в CI/CD | Обязательные `pytest + lint + typecheck` перед деплоем | Меньше прод-инцидентов, предсказуемые релизы |
| Укрепить сетевой слой | Timeout + retry/backoff, TLS verify ON | Меньше зависаний, выше отказоустойчивость интеграций |
| Упростить async/sync границы | Явный архитектурный boundary: adapter/orchestrator вместо размазанного `run_sync` в доменных сервисах | Ниже сложность поддержки, легче тестировать и профилировать |
| Убрать дублирование `inline/celery` веток | Единый планировщик тяжелых операций для всех handlers | Меньше дублирования, быстрее безопасные изменения в очереди |
| Привести обработку ошибок к стандарту | Убрать silent pass, добавить структурные логи и error-id | Быстрее дебаг, меньше "тихих" поломок |
| Централизовать auth-checks | Общий guard для callback/FSM маршрутов | Стабильное и предсказуемое поведение сценариев |
| Навести порядок в конфигурации | Полный `.env.example`, документация required/optional переменных | Быстрее запуск новых окружений, меньше ошибок конфигурации |
| Сделать зависимости детерминированными | Lock-файл и регулярное обновление через CI | Стабильные сборки, меньше сюрпризов при релизах |
| Усилить тестовую сетку | Тесты на критичные ветки: OAuth, `reply_employers`, API error paths | Раннее обнаружение регрессий и снижение стоимости изменений |
| Улучшить целостность данных | FK ON + базовые миграции в подмодуле | Меньше скрытых проблем в данных и отчетах |
| Актуализировать документацию | Обновить README, описать архитектуру и потоки | Лучшая поддерживаемость и onboarding |

## Рекомендуемый порядок внедрения (коротко)

1. Сначала закрыть все Critical/High по безопасности и надежности (секреты, TLS, timeout, баги в OAuth/`reply_employers`/`json.dump`).
2. Затем поставить quality gate и минимальные автотесты на критичные сценарии.
3. После этого довести конфиги/документацию и убрать технический долг в обработке ошибок и неиспользуемых ветках.
